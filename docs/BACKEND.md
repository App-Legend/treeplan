# 백엔드 정리 (성수연 · 서버 기능 구현)

중간발표용 정리. 기술 용어는 처음 나올 때 풀어서 적었다.
관련 문서: [API.md](API.md) · [DB.md](DB.md)

---

## 0. 30초 설명

> 섞어봄(Tree-Plan)의 서버를 맡았습니다. 사용자가 분야를 고르면 **AI가 단어 트리를 뻗어 주고**, 고른 단어 3개로 **AI가 아이디어와 실행안을 만드는** 과정을 서버에서 처리합니다.
> 로그인 없이도 쓸 수 있게 **게스트 모드**를 만들었고, 로그인하면 그동안 만든 결과가 히스토리로 옮겨집니다.
> AI가 느리거나 실패할 때를 대비해 **다른 AI 모델로 자동 전환**하게 만들었고, 일부러 실패 상황을 만들어 확인했습니다.

## 1. 백엔드 한눈에 보기

```
[브라우저: frontend-credit]
        │  /api/... 요청 (JSON)
        ▼
[Spring Boot API 서버]  ← 우리가 만든 것
   Controller  : 요청을 받는 입구 (주소별로 나뉨)
   Service     : 실제 규칙과 판단 (20개 제한, 권한 확인, AI 호출 …)
   Repository  : DB 읽기/쓰기
        │                         │
        ▼                         ▼
 [PostgreSQL DB]            [Gemini API (Google AI)]
  테이블 10개                단어·아이디어·실행안 생성
```

- **브라우저는 AI와 DB에 직접 접근하지 않는다.** 반드시 서버를 거친다 → AI 키가 브라우저에 노출되지 않는다(기획서 보안 요구사항).
- 기술: Java 21 + Spring Boot 3.5, Spring Security + JWT(로그인 토큰), PostgreSQL 16, WebSocket(실시간 알림), Gemini API

### 코드 폴더 (backend/src/main/java/com/applegend/seokkeobom/)

| 폴더 | 하는 일 | 대표 파일 |
|---|---|---|
| `auth` | 회원가입·로그인·게스트·토큰 | `AuthService`, `GuestMergeService`, `Accounts` |
| `session` | 세션·팀 코드·참여자·실시간 알림 | `SessionService`, `SessionEventPublisher` |
| `category` | 카테고리·하위 카테고리·**단어 트리** | `WordTreeService`, `CatalogService`, `Subcategories` |
| `draw` | 단어 3개 뽑기 | `DrawService` |
| `idea` | AI 아이디어 생성 | `IdeaService` |
| `result` | AI 실행안 생성·수정·보완·내보내기 | `ResultService`, `ExportService` |
| `history` | 히스토리 조회 | `HistoryService` |
| `ai` | Gemini 호출·프롬프트·대체 모델 | `GeminiAiClient`, `PromptBuilder`, `MockAiClient` |
| `seed` | 처음 실행 때 기본 데이터 넣기 | `DataSeeder` |

### 지금 실제로 무엇이 어디서 돌아가나 (로컬 실행 기준)

```
 브라우저 (http://127.0.0.1:5173)
     │
 ① 프론트 개발 서버 ─ node(Vite) · 포트 5173 · Docker 아님
     │  /api 요청만 백엔드로 넘김(프록시)
 ② 백엔드 ─ java(Spring Boot) · 포트 8081 · Docker 아님 (gradlew bootRun)
     │  .env에서 키·DB 주소·포트를 읽음
     ├──────────────────────────┐
 ③ DB ─ Docker 컨테이너           ④ Gemini API ─ 구글(인터넷)
   treeplan-db-1 (PostgreSQL 16)
   PC 포트 5434 → 컨테이너 5432
```

| 번호 | 무엇 | 실행 방식 | 포트 | 켜는 명령 |
|---|---|---|---|---|
| ① | 프론트 `frontend-credit` | PC에서 직접 (node) | 5173 | `npm run dev` |
| ② | 백엔드 `backend` | PC에서 직접 (java) | 8081 | `.\gradlew.bat bootRun` |
| ③ | DB | **Docker 컨테이너** | 5434 | `docker compose up -d db` |
| ④ | AI | 외부 서비스 | 인터넷 | 키만 있으면 됨 |

- **Docker에서 도는 것은 DB(PostgreSQL) 하나.** 사용자 정보뿐 아니라 세션, 단어 트리, 아이디어, 실행안 등 **서비스의 모든 데이터**를 저장한다.
- 데이터는 Docker 볼륨 `treeplan_pgdata`에 있어 컨테이너를 껐다 켜도 남는다 (`docker compose down -v`를 하면 지워짐).
- 실제로 쓰는 데이터베이스 이름은 `seokkeobom`. 테이블은 백엔드가 처음 켜질 때 자동으로 만든다.
- 포트가 기본값(5432·5433·8080)이 아닌 이유: 이 PC에서 다른 PostgreSQL이 5432·5433을 쓰고 있고, 8080은 실행이 막힌 적이 있어서 `.env`로 바꿨다. 다른 PC에서는 기본값으로 돌아갈 수 있다.
- `docker-compose.yml`에는 백엔드(`api`) 컨테이너 설정도 있다. `docker compose up -d --build`로 백엔드까지 컨테이너로 띄울 수 있다(배포·JDK 없는 PC용, 지금은 안 씀).
- Docker를 쓴 이유: 팀원마다 PostgreSQL을 설치하지 않아도 명령 한 줄로 같은 버전의 DB를 띄울 수 있다.

### 외부 API: Gemini 하나뿐

| 쓰는 곳 | 모델 |
|---|---|
| 단어 트리 가지 뻗기 | `gemini-3.5-flash-lite` (빠름, 약 1~2초) |
| 아이디어 생성, 실행안 생성·보완 | `gemini-3.8-flash` (품질, 약 10~15초) |
| 위가 실패할 때 대체 | `gemini-3.5-flash` → `gemini-3.1-flash-lite` |

- 모델은 여러 개지만 **같은 Gemini API, 같은 키 하나**로 부른다.
- 메일 발송, 소셜 로그인, 결제, 지도 같은 다른 외부 API는 **없다**.
- 헷갈리지 말 것: **우리가 만든 API**(화면이 부르는 `/api/...` 24개)와 **우리가 쓰는 외부 API**(Gemini 1개)는 다르다.

### 백엔드 안의 시스템 장치 (모두 Spring Boot 서버 하나 안에 있음)

| 장치 | 하는 일 | 기술 |
|---|---|---|
| 인증·보안 | 요청마다 토큰으로 누구인지 확인, 비밀번호 암호화 저장, 로그인 5회 실패 시 5분 잠금 | Spring Security, JWT, BCrypt |
| 실시간 채널 | 팀원 입장·퇴장, 가지 뻗기, 결과물 생성 알림을 서버가 먼저 보냄 | WebSocket + STOMP (서버 메모리 중계기) |
| 예약 작업 | 매일 새벽 4시(서울), 30일 활동 없는 세션을 만료 처리 | Spring `@Scheduled` (`SessionExpiryJob`) |
| 시작 작업 | 서버가 켜질 때 기본 카테고리·양식·하위 카테고리를 맞춤 | `DataSeeder` |
| 파일 내보내기 | 결과물을 PDF·TXT·MD로 생성 (PDF는 한글 글꼴로 서버에서 만듦) | OpenPDF |
| 예시(mock) AI | 키가 없으면 예시 결과로 대신 동작 (시연 대비·자동 테스트용) | `MockAiClient` |
| 중복 요청 방지 | 버튼 두 번 눌러도 세션 하나만 생성(멱등 키), 같은 가지 동시 뻗기 차단 | 요청 식별자, 서버 메모리 잠금 |
| 오류 처리 | 모든 오류를 `{코드, 한국어 메시지}`로 통일, 내부 오류 내용은 숨김 | `GlobalExceptionHandler` |
| DB 연결 | 자바 객체를 테이블에 저장, 테이블 자동 생성, 연결 재사용 | JPA/Hibernate, HikariCP |
| CORS | 허용한 프론트 주소에서 온 요청만 받음 | Spring CORS 설정 |
| 상태 확인 | `/api/actuator/health`로 서버 살아 있는지 확인 | Spring Actuator |
| 설정 관리 | 키·DB 주소·포트를 `.env`·환경변수에서 읽음, 코드에 비밀값 없음 | Spring 설정 import |

개발 도구: Gradle(빌드·실행·테스트), H2(자동 테스트 때만 쓰는 메모리 DB), Dockerfile·docker-compose(컨테이너 실행), Vite 프록시(프론트 → 백엔드 연결)

### 없는 것과 한계

| 없는 것 | 이유·상태 |
|---|---|
| 캐시(Redis 등) | 기획서에 근거가 없어 넣지 않음 (6주차 결정) |
| 메시지 큐 | 서버 1대 규모라 불필요 |
| 메일 발송 | 비밀번호 재설정은 접수만 |
| 파일 저장소 | 업로드 기능 없음, 내보내기 파일은 그때그때 생성 |
| 로그·모니터링 시스템 | 서버 콘솔 로그만 있음 |
| 배포·CI | 아직 로컬 실행만 |
| DB 마이그레이션(Flyway) | 없음, 사용자 테스트 전 도입 계획 |

> 한계: 실시간 채널과 "같은 가지 동시 뻗기 방지"는 **서버 메모리**에 있어서 **서버가 1대일 때만** 제대로 동작한다. 서버를 여러 대로 늘리려면 Redis 같은 공용 저장소가 필요하다. 수업 규모에서는 문제없다.

## 2. 핵심 기능 6가지

### ① AI 단어 트리 (가장 중요)
- 카테고리(음식·프로그램·공모전)마다 **고정 하위 카테고리 3개**가 트리의 뿌리.
- 뿌리나 단어를 누르면 → 서버가 Gemini에 "이 분야, 이 하위 카테고리에서 이 단어와 관련된 단어 3개" 요청 → 받은 단어를 저장.
- 규칙(서버가 확인):
  - 뿌리 하나에 **최대 20개**
  - 이미 트리에 있는 단어는 **다시 저장 안 함** (띄어쓰기·대소문자 무시하고 비교)
  - 같은 뿌리에서 동시에 두 번 누르면 하나만 처리
  - 트리는 **세션마다 따로** 자란다 (팀원은 같은 트리를 봄)
- API: `POST /words/{id}/expand`

### ② 단어 3개 뽑기
- 트리에서 직접 고른 3개 또는 무작위 3개(다시 뽑기).
- 트리에 단어가 3개 미만이면 막음 (기획서: "3개 미만 조합으로 생성하지 않는다").
- API: `POST /sessions/{id}/draws`

### ③ AI 아이디어 → 실행안
- 아이디어: 단어 3개 + 분야 → 제목과 2~3문장 요약.
- 실행안: 아이디어 + 분야별 양식(절차 템플릿) → 항목별 본문. 마지막 항목은 항상 **조합 이유**(기획서 신뢰성 요구사항).
  - 음식: 콘셉트 → 재료·분량 → 만드는 순서 → 주의점 → 조합 이유
- AI 응답은 JSON 형식으로 받아서 항목별로 나눠 저장.
- 프롬프트(AI 지시문)에 "세 단어 모두 쓰기, 진부한 결과 피하기, 사실·수치 지어내지 않기"를 넣음 → `PromptBuilder.java`

### ④ 게스트(비로그인) 모드
- 처음 들어오면 서버가 **임시 사용자(게스트)**를 만들어 토큰을 준다 → 로그인 없이 모든 흐름 사용.
- 실행안 응답에 `saved: false` → 화면이 "히스토리로 남기고 싶다면 로그인해 주세요" 팝업.
- 그때 로그인·가입하면 **게스트가 만든 세션·결과물을 새 계정으로 옮긴다** (`GuestMergeService`).
- 게스트는 히스토리 조회·팀 코드 입장 불가 (로그인 필요 기능).

### ⑤ 협업과 권한
- 팀 코드로 입장한 참여자는 결과물을 함께 보고 수정. 삭제·세션 종료는 **방장만**.
- 누가 가지를 뻗거나 결과물을 만들면 **실시간 알림**(WebSocket)을 보냄. (화면 수신은 아직)

### ⑥ AI 안정화 (실패 대비)
```
gemini-3.8-flash (품질 좋음, 평소 10~15초)
   │ 45초 넘거나 / 503 혼잡 / 429 할당량 초과
   ▼
gemini-3.5-flash (빠름)  →  실패하면  →  gemini-3.1-flash-lite (가장 빠름)
```
- 503은 같은 모델로 잠깐 뒤 1번 더 시도, 그래도 안 되면 다음 모델.
- 단어 생성은 원래부터 빠른 모델(`3.5-flash-lite`, 약 1~2초) 사용.
- 그래도 실패하면 화면에 실패 이유와 "같은 조합으로 다시 시도" 버튼.

## 3. 요청 하나가 처리되는 과정 (예: 가지 뻗기)

1. 화면이 `POST /api/words/15/expand` + `{sessionId: 3}` 전송 (헤더에 로그인/게스트 토큰)
2. `JwtAuthFilter`가 토큰을 확인해 누구인지 알아냄
3. `CategoryController` → `WordTreeService.expand()` 호출
4. 서비스가 확인: 세션 참여자인가? 세션이 진행 중인가? 이 뿌리가 20개 미만인가? 이미 뻗는 중인가?
5. 이미 있는 단어 목록과 함께 Gemini에 요청 (`GeminiAiClient`)
6. 받은 단어 중 중복·너무 긴 것 제외 후 DB(`word_nodes`)에 저장
7. 팀원들에게 실시간 알림 `TREE_EXPANDED` 발송
8. 새 단어와 남은 개수(`remaining`)를 응답

## 4. 평가 기준별 내 기여

### 기존 실습의 반영 (20점) — 기획이 어떻게 코드가 됐나

| 기획서 | 코드에 반영된 곳 |
|---|---|
| 3주차 요구사항: 3개 미만 조합 생성 금지 | `DrawService` — 트리 단어 3개 미만이면 `TREE_TOO_SMALL` |
| 3주차 요구사항: 결과에 입력 단어와 조합 이유 | 모든 양식 마지막 항목 `reason`(조합 이유) |
| 3주차 보안: AI 키를 브라우저에 노출하지 않음 | 키는 서버 `.env`에만, 브라우저는 서버만 호출 |
| 3주차 용어: 절차 템플릿 | `DataSeeder`의 분야별 양식 3개 |
| 4주차 위험 3: AI 장애·지연 | 대체 모델 자동 전환, 실패 시 재시도 안내 |
| 기획 변경: 하위 카테고리 3개, 뿌리당 20개 | `Subcategories`, `WordNode.MAX_WORDS_PER_ROOT = 20` |
| 기획 변경: 로그인 없이 작업, 결과 만들 때 로그인 권유 | 게스트 토큰, `saved`/`loginPrompt`, `GuestMergeService` |
| 기획 변경: AI를 단어 생성에도 사용 | `POST /words/{id}/expand`, `PromptBuilder.wordsPrompt` |
| 6주차 아키텍처: 상자 5개, 화살표 10개 | 그대로 구현. 클라이언트 → API 서버 → DB / Gemini |
| 6주차 데이터 10개 | 테이블 10개 ([DB.md](DB.md)) |
| 6주차 API 22개 | 24개로 구현 (게스트 시작, 가지 뻗기 추가) — 기획서도 수정함 |

**달라진 점 (설명할 것):** 처음 기획은 "미리 넣은 단어 풀에서 무작위"였는데, 단어가 금방 겹치는 문제(위험 1) 때문에 **AI가 단어를 만드는 방식**으로 바꿨다. 랜덤 하위 카테고리도 넣었다가 품질 때문에 **고정 3개**로 정리했다.

### 제품의 실제 동작 (30점)
- 핵심 흐름 전체가 실제 AI로 동작: 시작 → 분야 → 트리(자동 3개씩) → 3개 고정 → 아이디어(약 12초) → 실행안(약 12초) → 로그인 → 히스토리
- 자동 테스트 3개 통과 (`CoreFlowTest`: 핵심 흐름, 게스트 흐름, 인증 규칙)
- 프론트(`frontend-credit`)를 백엔드에 연결하고 브라우저에서 처음부터 끝까지 확인

### AI 활용과 검증 (20점) — AI 결과를 그대로 쓰지 않은 사례

| 상황 | 확인한 것 | 판단·수정 |
|---|---|---|
| 처음 받은 MVP 코드 | AI가 만든 코드가 **한 번도 실행된 적 없음**을 README에서 확인 | 직접 빌드·테스트 실행해서 동작 확인 후 진행 |
| 기본 AI 모델 | `gemini-2.5-flash`가 "새 사용자에게 제공 안 함"으로 실패 | 실제 호출로 사용 가능 모델을 조회해 `3.8-flash`로 교체 |
| AI 응답 속도 | 3.8-flash가 60~77초 걸림을 측정 | 단어 생성은 1~2초 걸리는 lite 모델로 분리 |
| 트리 화면 겹침 | 단어를 뻗으면 노드가 겹침 → 원인: 피그마 좌표 고정 | 단어 길이로 위치를 계산하게 바꾸고, 34개 노드 겹침 0건 확인 |
| 한 번에 만드는 단어 수 | AI가 임의로 5개로 정함 | **3개로 결정** |
| 랜덤 하위 카테고리 | 분야 밖 단어가 섞일 수 있음 | **고정 3개로 결정**, 기획서도 수정 |
| AI 실패 | 서버 로그 분석: 시간 초과 시 대체 모델로 안 넘어가는 문제 발견 | 코드 수정 후 **일부러 시간 초과를 만들어** 6번 모두 성공 확인 |
| API 키 관리 | 키를 코드에 넣자는 방안 검토 → 레포가 **공개**임을 확인 | `.env`(git 제외)로 관리, 커밋에 키 없음을 검사 |

> AI 도구(Claude Code)로 코드를 만들고, **실행·측정·로그 확인으로 검증**한 뒤 결정은 직접 했다는 흐름으로 설명하면 된다.

## 6. 예상 질문과 답

**Q. AI가 결과를 못 만들면 어떻게 되나요?**
A. 기본 모델이 45초 안에 답하지 않거나 혼잡(503)·할당량 초과(429)면, 서버가 자동으로 더 빠른 모델 두 개를 차례로 시도합니다. 그래도 실패하면 화면에 이유와 "같은 조합으로 다시 시도" 버튼이 나옵니다. 일부러 기본 모델을 계속 실패하게 만들어서 6번 모두 성공하는 것을 확인했습니다.

**Q. 왜 단어 생성과 아이디어 생성에 다른 모델을 쓰나요?**
A. 단어는 자주 누르기 때문에 빨라야 합니다. 측정해 보니 lite 모델이 1~2초, 품질 모델은 수십 초였습니다. 아이디어·실행안은 한 번만 만들고 품질이 중요해서 좋은 모델을 씁니다.

**Q. 같은 단어가 트리에 두 번 나오지 않게 어떻게 하나요?**
A. 두 단계입니다. AI에게 "이미 있는 단어는 쓰지 말라"고 목록을 함께 보내고, 받은 뒤 서버가 띄어쓰기·대소문자를 무시하고 한 번 더 비교해서 중복은 저장하지 않습니다.

**Q. 로그인 안 한 사용자의 결과는 어떻게 저장되나요?**
A. 처음 들어올 때 서버가 임시 사용자(게스트)를 만들고 토큰을 줍니다. 게스트가 만든 결과도 DB에는 있지만 히스토리에는 안 보입니다. 로그인할 때 게스트 토큰을 함께 보내면 서버가 그 결과들의 주인을 새 계정으로 바꿉니다.

**Q. API 키는 어떻게 보호하나요?**
A. 키는 서버의 `.env` 파일에만 있고 이 파일은 git에 올라가지 않습니다. 브라우저는 우리 서버만 부르고, 서버가 Gemini를 호출합니다. 그래서 브라우저 개발자 도구로 봐도 키가 보이지 않습니다.

**Q. 로그인은 어떻게 동작하나요?**
A. 로그인하면 액세스 토큰(30분)과 리프레시 토큰(14일)을 받습니다. 요청마다 액세스 토큰을 보내고, 만료되면 리프레시 토큰으로 새로 받습니다. 리프레시 토큰은 한 번 쓰면 폐기되고, 비밀번호는 암호화(BCrypt)해서 저장합니다. 로그인 5번 실패하면 5분 잠깁니다.

**Q. 팀원이 결과물을 지울 수 있나요?**
A. 아니요. 결과물 삭제와 세션 종료는 방장만 할 수 있고, 서버에서 확인합니다. 팀원은 보고 수정할 수 있습니다.

**Q. 뿌리당 20개 제한은 왜, 어디서 확인하나요?**
A. 화면이 너무 복잡해지고 AI 호출이 늘어나는 것을 막기 위해서입니다(기획서 결정). 화면에서도 막지만, 서버 `WordTreeService`가 저장 전에 개수를 세서 20개면 `ROOT_FULL`로 거절합니다. 화면만 믿으면 우회할 수 있기 때문입니다.

**Q. 테스트는 어떻게 했나요?**
A. 자동 테스트 3개가 있습니다. 가입부터 트리·뽑기·생성·수정·권한·삭제까지 전체 흐름, 게스트 흐름, 로그인 규칙을 확인합니다. 테스트 때는 실제 AI 대신 예시 AI를 써서 항상 같은 결과로 검사합니다. 추가로 실제 AI로 브라우저에서 끝까지 직접 확인했습니다.

**Q. DB는 어떻게 설계했나요?**
A. 테이블 10개입니다. 중심은 세션 → 추출 → 아이디어 → 결과물 순서입니다. 단어 트리는 한 테이블에서 "상위 단어 ID"로 자기 자신을 가리키는 구조입니다. 아직 외래 키가 없다는 한계가 있어서 사용자 테스트 전에 추가할 계획입니다.

**Q. Docker로는 뭘 돌리나요? 왜 썼나요?**
A. DB(PostgreSQL) 하나만 Docker로 돌립니다. 팀원마다 DB를 따로 설치하지 않아도 명령 한 줄로 같은 버전을 띄울 수 있어서입니다. 백엔드와 프론트는 개발하기 편하게 PC에서 바로 실행합니다.

**Q. 서버를 끄면 데이터가 사라지나요?**
A. 아니요. 데이터는 Docker 볼륨에 저장돼서 백엔드나 DB 컨테이너를 껐다 켜도 남습니다.

**Q. 외부 API는 뭘 쓰나요?**
A. Google Gemini 하나입니다. 용도에 따라 모델만 다르게 쓰고, 키는 하나입니다. 메일·소셜 로그인 같은 다른 외부 서비스는 쓰지 않습니다.

**Q. 실시간 알림은 별도 서버인가요? Redis 같은 건 안 쓰나요?**
A. 별도 서버 없이 Spring Boot 안의 WebSocket으로 보냅니다. 서버가 1대라 메모리로 충분해서 Redis는 쓰지 않았습니다. 서버를 여러 대로 늘리면 Redis 같은 공용 저장소가 필요합니다.

**Q. 30일 지난 세션은 어떻게 만료되나요?**
A. API가 아니라 서버 안의 예약 작업이 매일 새벽 4시에 활동 없는 세션을 찾아 만료로 바꿉니다.
